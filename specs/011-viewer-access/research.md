# Research: Invite codes and locked pages

## R1. Reaching Neon from the app and the commands

- **Decision**: call Neon's SQL-over-HTTPS endpoint with `httpx`. One module (`neon.py`) with `query(url, sql, params)` and `transaction(url, queries)`.
- **Wire format** (read from the open-source `@neondatabase/serverless` driver, `src/http/index.ts`):
  - `POST https://<host>/sql`
  - Headers: `Neon-Connection-String: <the postgresql:// URL>`, `Neon-Raw-Text-Output: true`, `Neon-Array-Mode: true`
  - Body for one query: `{"query": "...", "params": [...]}`. For a transaction: `{"queries": [{"query": ..., "params": [...]}, ...]}`, with the response `{"results": [...]}`.
  - Each result has `fields` (each with `name` and `dataTypeID`), `rows` (arrays of text values or null) and `rowCount`.
  - A failed query is HTTP 400 with `message` and `code`. Any other failure is a non-400 status.
- **Why**: no Postgres driver, so no new dependency (constitution IV), and it works from Vercel's Python runtime, which has no long-lived connections.
- **Open question, settled by task 1**: the driver notes say HTTP queries use the pooled host (`-pooler` after the endpoint ID). The stored URLs use the direct host. A spike against the `dev` branch decides whether `neon.py` adds `-pooler` to the host itself. That's a string change, with no infra change.
- **Alternatives considered**: `psycopg` (a new dependency, and TCP connections on serverless); `asyncpg` (same); Neon's Data API (needs more setup, and isn't on the free-plan path we've verified).

## R2. Roles and privileges

- **Finding**: phase 3 made only the owner roles (`rain_owner`, `rain_dev_owner`). The app role `rain_app` is created here, with the password already generated by OpenTofu (`random_password.app_*`), as `research.md` R2 of spec 010 planned.
- **Decision**: `viewer init --env dev|prod`, run by the owner, creates `rain_app` with `CREATE ROLE … LOGIN PASSWORD`, then creates the tables and grants only:
  - `viewers`: SELECT, and UPDATE on `last_login_at` only
  - `viewer_pages`: SELECT
  - `sessions`: SELECT, INSERT, DELETE
  - `login_attempts`: SELECT, INSERT, UPDATE, DELETE
- **Why**: the hosted site never creates, revokes or changes a person (FR-001, no owner controls). A stolen app URL can't invite itself or promote itself.
- **The password**: it comes from the app URL in the owner's `.env` (`VIEWERS_APP_URL_<ENV>`). It's alphanumeric, because the OpenTofu resource uses `special = false`, and `init` refuses anything else before putting it in SQL.
- **Getting the URLs onto the Mac**: phase 3 outputs only the owner URLs. This phase adds `dev_app_url` and `prod_app_url` as sensitive outputs. That changes no resources, so the apply only updates the state. It runs once from this branch with **Run workflow**, which now works because `infra.yml` is on `main`.
- **Alternatives considered**: giving the site the owner role (too much power); creating the role in OpenTofu (the Neon provider makes it a `neon_superuser` member, see spec 010 R2).

## R3. Code format and hashing

- **Decision**: 16 characters from a 54-letter-and-digit alphabet with no look-alike characters (no `0 O o 1 I l`), about 92 bits, shown as `xxxx-xxxx-xxxx-xxxx`. Dashes and spaces are ignored on entry. The case matters. Stored as the SHA-256 of the cleaned code, compared with `hmac.compare_digest`.
- **Why SHA-256**: a code this random can't be guessed from its hash, so a slow hash adds nothing. A salt-free hash also lets the login look the person up by hash with one indexed query. `scrypt` (the security options page's suggestion) would need a per-person salt, so each login would check every person, at about 50 ms of CPU each, against the 4-hour monthly CPU limit.
- **Spec check**: FR-002 asks for at least 12 characters. 16 meets it.
- **Alternatives considered**: `scrypt` per person (above); a keyed hash (the owner's Mac doesn't hold the site's signing secret).

## R4. Sessions and the cookie

- **Decision**: the cookie holds `<session id>.<signature>`. The session id is 32 random bytes, URL-safe. The signature is HMAC-SHA256 of the id with `SESSION_SECRET`. The database holds only the SHA-256 of the id, with the person, the start and the end (30 days). The cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, and has a matching max age.
- **Why**: the signature rejects forged or edited cookies without a database call (FR-011, edge case). The row lets revoke and log out end a session (FR-005, FR-012). Hashing the id means a database read can't be turned into a working cookie.
- **Local testing**: browsers refuse a `Secure` cookie on plain `http` except for `localhost`. Chrome accepts it there. The cookie is marked `Secure` whenever the request is HTTPS or the host is `localhost` or `127.0.0.1`.
- **Alternatives considered**: a signed cookie with no database row (can't be revoked); `SameSite=Strict` (breaks links from email).

## R5. Deny by default, and which page unlocks which route

- **Decision**: `access.py` holds three things: the page keys, the starting pages for each tier (from the spec's Assumptions), and `API_ACCESS`, a table of `(method, path)` to the page keys that unlock it. A request is allowed if the person's pages include any of them.

  | Route | Unlocked by |
  |---|---|
  | `GET /api/overview` | `overview` or `new-artists` (both pages use it) |
  | `GET /api/genre`, `GET /api/genre/songs` | `genre` |
  | `GET /api/artist` | `artist` |
  | `GET /api/sql/meta`, `POST /api/sql`, `GET /api/schema` | `analyst` |
  | `GET /api/health` | public (hosted: returns only `{"ok": true}`) |
  | `GET /api/me`, `POST /api/login`, `POST /api/logout` | public (they do their own checks) |
  | everything else under `/api` | refused |

- **Startup check**: on start-up, every route FastAPI has registered under `/api` must be in `API_ACCESS` or be refused on purpose (the playlist, AI and write routes the phase 2 guard already refuses). A missing route stops the app from starting. That makes FR-017 ("a route with no declaration is refused") hold by construction, and also catches it in the phase 6 deploy.
- **Static pages**: see Complexity Tracking in the plan. Pages that load no data are shown or hidden by the browser app.
- **Alternatives considered**: a decorator on each route (easy to forget one, and no single list to review); FastAPI dependencies (same).

## R6. Checking a session on each request

- **Decision**: one query joins the session, the person and their granted pages:
  `sessions` → `viewers` (status, tier) → `string_agg` over `viewer_pages`. The answer is cached in memory for 3 seconds, keyed by the session id hash.
- **Why**: one Neon call per request would add latency and wake the database often. A 3-second cache makes a page that makes six API calls cost one query, and keeps revocation inside the spec's 5 seconds (SC-004) on every server instance.
- **Waiting costs no CPU**: Vercel's active CPU time doesn't count while a function waits on a network call.
- **Alternatives considered**: a longer cache (breaks SC-004); caching in a signed cookie (can't be revoked); no cache (up to 6 queries per page view).

## R7. The login rate limit without raw IPs

- **Decision**: the source is the first address in `x-forwarded-for` (or the connection address locally). The stored key is `HMAC-SHA256(SESSION_SECRET, day + ":" + address)`, hex, so it changes every day and can't be turned back into an address without the secret. One row per key in `login_attempts` holds the failure count, the start of the minute window and a lock-out time.
- **Rules**: more than 5 wrong codes inside one minute: refuse further tries in that minute without checking (HTTP 429). 20 wrong codes in a day: lock out for 15 minutes, including correct codes. A correct code from another source is unaffected. Rows older than a day are deleted when anyone logs in.
- **Why**: meets FR-014 and the constitution (no raw IPs) with no extra service.
- **Alternatives considered**: counting in memory (each serverless instance would count separately, so the limit would leak); counting by the code tried (an attacker can vary the code).

## R8. Requests from other sites

- **Decision**: `POST /api/login` and `POST /api/logout` check the `Origin` header. If it's present and its host differs from the request's host, refuse (403). The login cookie is `SameSite=Lax`, and no `GET` changes anything.
- **Why**: FR-013, and the security options page's "check Origin on every POST". There are no other state-changing routes on the hosted site.

## R9. The commands

- **Decision**: a `viewer` command group with `init`, `add`, `list`, `revoke`, `grant` and one required-by-default `--env` flag: `dev` unless `prod` is given. Every command prints a first line `[dev]` or `[prod]`. The owner URL for the chosen branch comes from `.env` (`VIEWERS_OWNER_URL_DEV` / `_PROD`). They run only on the Mac because the owner URLs exist only there, and the hosted site has no route that calls them.
- **Details**: [contracts/cli.md](contracts/cli.md).

## R10. The browser app

- **Decision**:
  - `AuthProvider` calls `GET /api/me` once and holds `{name, tier, pages}` (or `{local: true}` locally, which allows every page).
  - `RequireAccess page="genre"` wraps each route. Not logged in goes to `/login?next=…`. Logged in without the page shows `NotAvailable`.
  - `SECTIONS` and the dashboard links are filtered by the person's pages.
  - Any API answer of `403 login_required` sends the person to the login page, so an expired or revoked session lands there on the next click. A new `ApiError` kind, `locked`, carries it.
  - A Log out button sits in the top bar.
- **Why**: the nav and guards are conveniences (FR-020). The server is the lock.
- **Alternatives considered**: a server-rendered login (the app is a static single-page app); keeping the pages array in the cookie (a grant change wouldn't apply until the next login, which breaks FR-021).

## R11. Testing

- **Decision**: no test suite, as in earlier phases. A quickstart with `curl` checks, SQL cross-checks on the dev branch, and a headless-Chrome run. The browser run uses a test tool started with `npx`, which stays out of the project's dependencies.
